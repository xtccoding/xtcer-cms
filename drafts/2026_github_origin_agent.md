# GitHub 宕机 7 小时背后：Agent 时代的代码托管之争，Cursor Origin 想颠覆什么

## 一次暴露单点风险的宕机

美东时间 2026 年 8 月 17 日上午 9 点 40 分，GitHub 官方确认正在调查"影响部分服务的性能问题"。故障迅速扩散：API 请求、Actions、Webhooks、Issues、Pull Requests 接连报错，登录用的 SAML、OIDC、SCIM 身份认证和 Team Sync 也受影响，连 Copilot 都没幸免。

据 GitHub 状态页披露，当天 Web 与 API 流量错误率一度接近 20%，归档和原始仓库下载的错误率逼近 50%。整个故障持续约 7 小时，其中核心服务中断约 3 小时。全球开发者在这几小时里无法拉代码、跑 CI、提交 Issue、发起 PR，连 AI 补全都停了。

一家掌握"全球绝大多数团队权威代码源"十余年的平台，暴露出了代码世界中枢纽带的单点脆弱。

## 同一天，Cursor 放出了 Origin

几乎同一时间，Cursor 正式宣布代码托管平台 Origin 向所有付费用户开放测试版。官方定位是"为 Agent 时代设计"的代码托管平台，不是编辑器套一层云壳：支持建仓库、标准 git 操作、发起 PR、合并、权限管理，还能把 GitHub 仓库整体镜像过来。

其中最受关注的是一个 **"Detach from GitHub"** 按钮——点击后即可把 Origin 设为权威数据源，完成主客易位。

据媒体报道，Origin 的发布属于既定计划，与 GitHub 故障的时间重合更可能是巧合。但两件事放在一起，信号非常明确：**GitHub 的瘫痪是导火索，Cursor 真正要争夺的是"权威数据源"这个位置。**

## 为什么"权威源"这个位置现在可以被挑战

因为底座的使用者群体正在改变。

Cursor 联合创始人 Michael Truell 今年 3 月公开过一组数据：Cursor 内部合并的 PR 中，35% 由运行在云端虚拟机上的自主 Agent 完成。Agent 自己开分支、自己提交、自己发起 PR。

GitHub 的工作流设计于 2008 年，核心面向"人"：一个人写完代码，找一两个人审查，排队等待合并，节奏以小时和天计算。Agent 不遵循这个节奏——十几个 Agent 同时涌入一个仓库，时间尺度是秒。

Origin 发布会公布的性能数据指向的正是这个场景：每小时 29.6 万次 clone、8.1 万次 push，单仓库每秒 22.6 次 commit，全球同步延迟低于 400 毫秒，自动故障转移 10 毫秒。每秒 22 次 commit 对人类的开发节奏来说夸张，但对成规模的 Agent 集群，这正是它们工作模式所需的吞吐。

GitHub 处理多 Agent 并发也相当吃力：十个 Agent 各改一批代码、各自提交 PR、CI 全部通过，先合并哪个？合并一个之后其余九个的测试结果还成立吗？传统方案是反复 rebase、合并冲突、CI 重跑。Origin 的合并队列支持自动排序和冲突检测，保证主干 CI 始终为绿，并在合并层内置 AI 引擎自动解决冲突。它还有原生 MCP 支持，Agent 可以像调用 API 一样驱动整个平台，不局限于 IDE 内部。

## Origin 凭什么有资格挑战

如果只是 Cursor 一家做代码托管，市场只会把它当作又一个 GitLab 或 Bitbucket。但 2026 年的 Cursor 握着几样别人难以复制的资源：

- **资金和算力。** 6 月 SpaceX 在纳斯达克 IPO 后行使收购选择权，以 600 亿美元全股票交易收购 Cursor 母公司 Anysphere，8 月 14 日正式完成。Cursor 并入 SpaceX AI 部门，与 Grok 团队同体系，还拥有一个在十万张 GPU 上从零训练的 1.5 万亿参数自研模型。"编辑器—模型—托管—Agent"全线贯通，是典型的垂直整合。
- **团队。** 2025 年 12 月 Cursor 收购了代码审查初创公司 Graphite，Origin 正是由 Graphite 团队主导开发。堆叠式 PR、合并队列这些概念，Graphite 已经实践了数年。

## 寄生式进攻：先镜像，再一键 Detach

GitHub 最大的护城河是沉淀十几年的生态：几乎每个开源项目、每套 CI 配置、每个开发者的使用习惯都扎根在 GitHub 上。托管功能本身反倒是次要的。短期内没有团队会把核心项目整体迁走。

Origin 的进攻策略可以概括为"寄生"：先以 GitHub 为权威源镜像仓库，让用户在 Cursor 里自然用起来；等用户习惯了、Agent 也开始在上面运行之后，再提供 "Detach from GitHub" 的选项，完成权威源的切换。渐进式策略比正面硬刚要有效得多。

当然 Origin 远非无懈可击：测试版还没上线堆叠式 PR、合并队列等核心差异化功能；生态方面首批接入方只有 Vercel、Depot、Buildkite 等，与 GitHub 庞大的 Actions 市场差距明显；微软手里有 Azure、Copilot 和全球最大的开发者关系网络，一旦感受到实质威胁，反应速度和资源体量都不容低估。

## 对我们开发者的启示

对个人和小团队，眼下合理的做法是去试用 Origin——尤其已经在用 Cursor 云端 Agent 跑后台任务的团队，迁移成本几乎为零。试一下"为 Agent 设计的底座"和"为人类设计的底座"之间到底差在哪，没什么风险。

更值得记住的是这件事本身：GitHub 用了十几年证明"代码应该集中托管"，而 Agent 时代正在把同样的集中式基础设施推向极限。单点权威源被重新争夺，说明**下一轮开发工具竞争的关键词是"吞吐、并发、自治"**，而不是"审查、排队、审批"。

代码世界的"权威数据源"，第一次有了一个具备实质竞争力的挑战者。过去十几年，开发者默认代码存放在 GitHub，这件事不需要思考。现在，它开始需要思考了。
